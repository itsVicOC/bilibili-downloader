# BiliFlow 迭代计划

制定日期：2026-10-15；版本进展更新于 2026-10-19，当前版本基线为 `v0.8.2`。本文描述后续拟实施的工作，不表示相关能力已经发布；实际交付以 Release 和更新日志为准。下表版本号保留制定时的建议里程碑，后续实施时重新排定。

`v0.8.1` 已交付 full 原生安装器和更新安装验证；`v0.8.2` 增加主题、工作区背景、批量解析容错及交互优化，背景副本纳入更新备份与回滚。媒体库、独立补全和订阅仍属于后续计划；长时直播、首次环境诊断、商业签名与公证等验收项继续按实际记录跟踪，不因维护版发布自动视为完成。

## 1. 产品目标与排期假设

面向以点播收藏为主、兼有少量直播保存需求的桌面用户，逐步完善“保存 → 核对 → 补全 → 持续更新 → 找到并使用”的工作流。

主线优先级：

1. 可靠交付与恢复：安装、更新、下载和录制的异常均有可验证的恢复路径。
2. 独立媒体库：清理任务记录后，仍知道本地保存了什么。
3. 增量补全：补字幕、封面或元数据时复用已有媒体。
4. 轻量订阅：对用户选择的少量来源检查新增内容。
5. 本地检索：按作品、作者、合集和字幕内容找回收藏。

排期按 **1 名核心维护者、每周 3–4 个有效开发日、每轮 2 周**估算。主线共 10 轮、20 周，另保留 4 周用于接口变化、跨平台问题和用户反馈，总体预算为 **约 24 周**。周数从实际启动算起，不是日历发布日期承诺；每轮按可用产能调整，未通过验收的内容顺延。

Windows x64 与 macOS ARM64 是本计划的安装包验收平台；Linux 继续保持源码与 CI 验证。Linux/Intel Mac 新安装包、后台服务和 NAS 部署由实际需求决定后续优先级。

### I1：先确认可靠性基线

- **R01 更新稳定化（P0）**：在两平台验证 full/lite 对应升级、活动任务收尾、取消、只读目录、安装失败和启动失败恢复；保留现有源码/Linux 手动更新入口。
- **R02 直播实测（P0）**：两平台分别用 full 包完成双路至少 8 小时录制；归档内存、界面响应、片段可读性、音视频轨、时间戳及缺口记录。补做断网、进程强退、睡眠、目录失效和测试卷空间不足验证。
- **R03 首次诊断（P1）**：集中检查工具、输出目录写权限、剩余空间和登录状态，给出具体修复入口；安装入口突出 full 包。
- **R04 安装信任（P1）**：落实签名/公证所需账号、证书和费用；条件具备时接入发布流水线。条件未具备时记录未完成项，发布说明准确表达签名状态，不宣称已完成。
- **R05 升级兼容预研（P0）**：确定未来 `library.sqlite3` 的备份、安装目录保护和恢复规则，验证从旧版更新程序进入新版的路径，必要时规划桥接版本。

本轮结束产出一份带包摘要、系统版本、日期和逐项结果的验收记录。失败项目附复现步骤和处理结论，不能以 CI 通过替代真实安装包验收。

### I2–I3：建立独立媒体库

- **A01 数据模型（P0）**：新增独立资产仓储，记录来源身份、实际媒体规格、文件位置、附加产物及核对状态。任务列表清理只影响任务。
- **A02 完成入库（P0）**：GUI 和 CLI 通过共享服务登记成功媒体；附加项部分失败仍登记媒体和缺失项。登记失败保留文件并提示，可在后续核对中恢复。
- **A03 历史导入（P0）**：优先利用现有任务、`.info.json` 和录制 `manifest.json`，提供导入预览。没有可靠身份的普通文件标记“待确认”，不根据文件名自动判断已拥有某作品。
- **A04 文件核对与去重（P0）**：按用户选择的目录核对已有文件，区分可用、缺失、不可访问、待确认和规格不满足；同一来源可拥有多个规格或文件副本。
- **A05 媒体库界面（P1）**：提供作品列表、作者/合集/状态筛选、打开文件、定位目录和核对操作。直播片段关联原场次及缺口信息，不将有缺口场次显示为完整保存。

第一版只核对用户明确选择的目录。长扫描在后台进行，可取消；取消或目录临时离线不能直接把整库标记为文件丢失。文件迁移/重命名先支持重新定位，自动整理另行排期。

### I4–I6：把补全和归档交付做好

- **A06 独立补全（P0）**：支持仅补字幕、封面、元数据；各附加项可独立失败和重试，已有媒体不重新下载、不重新封装。
- **A07 规格策略（P0）**：分别记录请求规格与实际规格；用户选择“允许回退并提示”或“严格匹配”。已有 1080P 不能被当成满足 4K 收藏目标。
- **A08 原始数据（P1）**：按用户选项保留源弹幕 XML、字幕 JSON 与 ASS/SRT 派生文件，记录来源、采集时间和转换版本。明确接口覆盖边界；高级弹幕无法完整转换时显示说明。
- **A09 NFO 导出（P1）**：从本地元数据生成 NFO 和约定目录结构，先选择 Jellyfin 的具体版本完成实际导入验证；只有验证后才声明相应兼容范围。对远端文本进行 XML 转义，生成采用原子写入，已有用户文件的处理必须有明确策略。
- **A10 归档试用（P0）**：邀请 8–12 位用户分批参与探索性试用，覆盖首次下载、收藏夹维护和直播保存；I2 起招募，I6 集中处理阻塞问题。试用不能替代发布门槛测试。

附加项补全仍遵循当前账号权限和受信任域名边界。源已不可访问时显示原因并保留本地文件。介质损坏时先提示修复/重新下载，不能把失效文件作为成功复用依据。

### I7–I8：引入受控的轻量订阅

- **S01 来源订阅（P1）**：首批支持现有解析器已覆盖的收藏夹与 UP 合集/系列，保存来源、输出策略和检查状态。
- **S02 首次扫描（P0）**：展示数量、范围及预览；由用户选择历史范围与是否下载，默认不自动拉取全部历史。
- **S03 增量检查（P0）**：用稳定内容身份比对，结合媒体库判断缺失和规格不满足；失败下载继续保持待处理，不因已被扫描就跳过。
- **S04 调度与退避（P0）**：先交付手动检查，再支持应用运行期间定期检查。限制请求频率和每轮分页/任务预算，使用随机偏移和错误退避；遵循已有风控冷却及接口响应。
- **S05 状态与提醒（P1）**：显示最近成功检查、扫描是否完整、下次检查和失败原因。仅对有新增、失败或需要处理的结果提醒；重复扫描不重复提醒。

分页中断不得提交“全量扫描完成”状态。远端删除、移出收藏或暂时失效只更新来源状态，不自动删除本地媒体。应用退出、睡眠期间不执行定期检查；恢复时按请求预算继续，不集中补发错过的轮次。

### I9–I10：验证持续使用价值

- **F01 本地检索（P1）**：支持标题、作者、合集和已保存 SRT 的正文检索，结果包含片段与时间点。按文件版本更新索引，删除/替换字幕后清理旧结果。
- **F02 播放衔接（P1）**：首先提供打开文件和复制时间点；优先适配一种经过验证的外部播放器进行时间点跳转，其他播放器保留通用入口。
- **U01 来源入口（P1）**：自动识别单视频、整季、收藏夹、合集和直播链接，引导至对应工作区；复用现有解析与权限判断。
- **U02 输出预设（P1）**：提供兼容优先、节省空间和最高可用规格等预设，展示实际可用编码及回退策略。预设只选择可用源流，不暗示内置转码能力。
- **F03 持续使用验证（P0）**：I7 起邀请用户试用订阅，连续观察至少 4 周；I10 汇总人工干预、重复下载、检索与继续使用情况，决定 1.0 范围。

若容量不足，先保留可靠检索与基本入口改进，时间点播放器适配和额外预设顺延。

## 4. 架构与数据约束

### 4.1 将任务、资产和来源分开

| 对象 | 负责回答的问题 | 关键内容 |
|---|---|---|
| 任务 | 本次操作进行到哪里？ | 操作类型、状态、进度、错误、恢复信息 |
| 内容 | 保存的是哪个作品或片段？ | BV/CID、EP 等稳定身份与别名；直播场次/片段身份 |
| 媒体资产 | 本地实际拥有什么？ | 实际画质/编码/音轨、文件路径、大小、可用性和核对时间 |
| 附加产物 | 哪些资料已保存或还需补全？ | 字幕语言、原始数据、派生文件、状态、来源时间和转换版本 |
| 订阅来源 | 哪些内容需要持续检查？ | 来源身份、策略、分页状态、检查时间、预算和退避 |

初步采用独立 `library.sqlite3` 保存媒体库，后续订阅表沿用该仓储。具体 schema 在 I2 固化。复用现有 `DownloadService`、`TaskRepository`、`LiveRepository` 和解析器，逐步增加服务边界；不同时重写下载、录制和 GUI。

来源身份应支持别名映射，例如同一番剧条目的 EP 与 BV/CID 信息，避免仅因入口不同就重复收藏。请求规格用于目标判断，实际规格用于资产登记；精确重复、可复用、可升级与文件缺失应有不同结果。

### 4.2 迁移和恢复先于正式发布

- 数据库迁移前备份；幂等导入同一任务或清单，不能产生重复资产。
- 处理数据库写入与文件落盘之间的中断：启动核对能补登记已完成文件，也能发现未完成产物。
- 更新备份覆盖配置、任务库、直播库及新媒体库；使用一致的 SQLite 备份方式处理 WAL，确认运行连接已释放。
- **专门测试旧版本携带的更新程序**：当前 `DATA_FILES` 只列出 `config.json`、`tasks.sqlite3`、`live.sqlite3`。升级路径须覆盖新数据库，不能仅修改新版清单后就假定旧版升级安全。首次引入媒体库需要桥接升级或等效自备份/恢复方案，并验证旧 beta、正式版和手动安装三种入口。
- 安装目录数据保护也须识别媒体库引用的文件；任务记录被清除后，仍不能因更新替换程序目录而误删媒体。
- 资产元数据提供有版本的便携清单导出，在数据库损坏时提供重建路径；保留用户对附加元数据文件的保存选择，未导出清单的记录从完整数据库备份恢复。用户标签等本地信息也应进入备份/导出，不能只依赖远端可重新解析。
- 清理任务、移除订阅和删除索引不删除媒体。若未来提供删除文件，单独设计并验收。

### 4.3 规格、完整性与隐私

- 区分文件存在、可读取、轨道/时长符合预期、附加项完整和目标规格满足，不能用一个“完成”掩盖差异。
- 哈希用于发现本地文件变化，不能据此宣称远端内容真实性；大文件核对按需执行，避免每次打开媒体库都读取整个视频。
- 不把完整历史弹幕、直播无缺口或所有播放器兼容作为未经验证的承诺。
- 现有 Cookie 白名单、系统凭据库、日志脱敏、网络目标验证和权限判断继续适用于新功能。
- 字幕索引保存在本地，支持关闭与重建；诊断导出默认不包含字幕正文、Cookie、签名播放地址和个人路径。

## 5. 发布门槛与验收方法

下列标准是拟采用的验收目标，不是现有达成数据。每条结果都记录构建版本、系统、输入夹具或授权来源、预期和实际行为。

| 门槛 | 必须通过的检查 |
|---|---|
| **G1 可靠性交付** | 两平台干净环境安装/更新/录制/导出通过；full/lite 和升级失败恢复通过；各平台双路至少 8 小时录制及故障记录归档；已知关键数据丢失、覆盖和凭据泄露问题归零 |
| **G2 数据安全** | 旧任务、旧清单、重复导入、中断迁移、数据库损坏及新版数据库保护验证；旧更新程序升级与回滚路径验证；已有媒体保持可访问 |
| **G3 独立补全** | 对有效已有媒体，仅补字幕/封面/元数据时媒体流下载请求数为 0、原媒体字节不变；附加项失败可重试；缺失媒体和权限不足给出明确处理路径 |
| **G4 归档正式版** | 清任务后重复导入不重复下载；移动/缺失/离线目录不被误判为可用；媒体和附加项可分别核对；NFO 通过指定版本媒体中心实测；试用阻塞问题已处理 |
| **G5 订阅** | 首次扫描确认、无新增重复检查、分页中断、来源删除、下载失败、限流和重启场景通过；不自动删除本地媒体；冷却不被重启或手动操作绕过 |
| **G6 1.0** | 完整执行“订阅新增 → 保存 → 中断恢复 → 补全 → 清任务 → 重启 → 搜索 → 打开”及升级恢复；完成至少 4 周订阅试用观察；无未解决的关键数据完整性问题 |

每次行为改动补充能验证相应风险的测试，网络测试使用脱敏 mock/fixture。按贡献指南完成完整回归；GUI 变更覆盖深浅主题和三种窗口尺寸，并对目标平台做原生检查。实际录制故障测试使用可控测试环境和有权保存的来源，不能用模拟状态转换代替全部实测。

建议记录以下用户指标，先建立基线，再决定改善目标：

| 指标 | 口径与用途 |
|---|---|
| 首次完成时间与成功率 | 从启动到第一个符合预期的可用文件；内容无权限、源不可用和产品错误分别计数 |
| 无需人工恢复的比例 | 可恢复网络/进程中断中，应用自行恢复完成的比例；明确故障样本和数量 |
| 重复媒体传输 | 同规格重复导入与仅补附加项场景是否发生无效媒体传输 |
| 录制缺口可解释性 | 中断是否留下正确时间范围和原因；源断流、睡眠和应用异常分别归因 |
| 本地查找成功率 | 用户能否找到指定作品或字幕片段，记录用时及失败原因 |
| 持续使用情况 | 受邀试用用户在第 2/4 周是否继续维护收藏，以及放弃的原因 |

试用采用用户主动提供的脱敏记录和访谈，不默认新增遥测。8–12 人用于发现问题和验证方向，不能据此推断市场占有率或总体留存率。

## 6. 依赖、分工与范围调整

核心依赖为：**更新/恢复机制 → 资产索引 → 长期去重 → 独立补全 → 来源增量检查 → 定期调度**。字幕检索依赖产物索引；同一维护者按迭代串行实现，长时测试和用户试用的观察期穿插执行。

- 核心维护者负责实现、迁移、发布和记录结论；每轮开始时从本轮任务中确定具体可交付项。
- 两平台实机验证由维护者或志愿测试者执行，尚未取得测试结果时如实保留未完成状态。
- 证书、公证账号和用户招募属于外部依赖，在 I1 启动准备；单独跟踪，不把未取得的条件写成已完成。
- 每轮结束提交可运行构建、对应测试/验收记录及文档；安排下一轮前检查范围、遗留问题和剩余容量。
- 4 周缓冲用于不可预期问题，优先保护迁移、恢复和数据完整性。超出预算时顺延功能，避免压缩这些验收。

范围调整顺序：

1. 保留数据安全、长期去重、独立补全和故障恢复。
2. 时间不足时，先顺延额外 NFO 方言、播放器时间点适配、额外预设和界面装饰调整。
3. 订阅先保证手动检查可靠，再开放定期检查；扫描不完整或限流行为未验证时维持手动模式。
4. API 兼容故障进入维护优先级，受影响来源暂停自动检查并说明状态，其他本地管理能力继续可用。

## 7. 后续候选与首轮开工清单

以下能力暂列后续候选：Linux/Intel Mac 安装包、后台常驻与 NAS、直播弹幕、更多直播编码、外部自动化接口/MCP、更多内容来源。通过需求频率、实现成本和维护负担重新排序后再进入迭代。

多平台直播、完整剪辑器、自动投稿、云录制和 AI 摘要不纳入本次 1.0 主线。若后续用户需求成立，先评估与既有工具的接口协作。

- [ ] R02：按直播文档执行长时和物理故障测试，补充缺口、内存及文件可读性记录。
